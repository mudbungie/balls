Found during bl-1fc4: mutate_author reads the live id set ('existing') from the store checkout while Create::stage writes into the change worktree opened at that checkout's HEAD. They agree by construction today — the seal merge --ff-only advances the checkout itself — but nothing states the invariant. If a future op ever advances balls/tasks by plumbing without moving the checkout, the 'found N new task files' finalize errors return with no obvious cause. Deliverable: name the invariant where the change worktree is opened (and/or in docs/architecture.md's op-atom section) so a future change that breaks it trips over the sentence; optionally a debug assertion that the change worktree's base equals the checkout HEAD at open.
