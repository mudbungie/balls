`bl list --all` / `-s closed` is O(dead x history) — measured 7.4s for 403 rows
(395 dead) on this store's 1193 commits, projecting to tens of minutes at a 5k
closed backlog. That is the one read path in balls that is structurally, not
tunably, slow, and it was raised as a feature gap against beads (SQL over Dolt).

## The diagnosis: not the storage model, the process fan-out

`src/reads/history.rs::dead_balls` runs ONE
`git log --diff-filter=D --name-only -- tasks` to enumerate every deleted
`tasks/<id>.md` — then throws away the commit sha it just learned and calls
`resolve_dead(store, id)` per ball, which re-runs
`git log -1 --diff-filter=D -- tasks/<id>.md` to re-derive that same sha, plus a
`git show`. 791 subprocesses where 2 suffice.

Worse, each per-id log walks from HEAD until it reaches that ball's deletion, so
cost scales with the ball's AGE (measured: 0.002s for the newest dead ball,
0.030s for the oldest, 1193 commits back). History length grows with ball count,
so the total is effectively O(N^2).

## The fix is a subtraction

Keep the sha and date from the walk that already found them (`--format` on the
existing enumeration), and resolve every pre-deletion blob in ONE
`git cat-file --batch` fed `<sha>^:tasks/<id>.md`. Measured on this store,
same data, same output:

    enumeration walk (1 process)   0.064s
    cat-file --batch (1 process)   0.023s
    total                          0.087s     vs 7.4s  = 85x

O(history + dead) instead of O(dead x history); ~1s projected at 5k closed.

## Why NOT an index, and why not a database

The §0 rule stands: never add an index unless indexing is the app. Nothing new
is stored, nothing is cached, no schema — the fix DELETES redundant work rather
than adding a second representation of it, so there is no drift surface. The
live path needs nothing either: `bl list` over 5000 live files measures ~0.1s,
where a query planner buys nothing. The beads comparison named the storage
substrate; the substrate was never the problem.

`resolve_dead` STAYS as the single-id path (`bl show <dead-id>`) — one walk for
one id is already right there. Only the plural path changes, and §9's
reconstruction semantics are preserved exactly: newest deletion wins, ids live
again are skipped, retirement date comes from the deletion commit.
