Found while landing bl-ffbf (chore rollback). Core's un-seal is git reset --hard <pre-op tip> on the store — LOCAL only. But any plugin that shells a nested bl op (bl-chore's claim.post create) triggers that nested op's create.post tracker PUSH. So an aborted claim in a tracked repo leaves the claim commit (and the nested create) already published; the next sync fast-forwards the aborted op straight back in. §14's 'core never pushes, so there is nothing remote to chase' stopped holding the moment any plugin shells bl. bl-ffbf's rollback closes the minted children, which narrows the damage to the shared record's claim commit itself. Design dialogue needed, not a first-draft fix — candidate directions to attack: (a) nested ops inherit the parent op's atom and defer their push until the parent seals (push becomes part of seal, one commit point per repo per op extends across nesting); (b) sync becomes convergence-aware of aborted ops (smells like a branch on a symptom); (c) accept and document that a tracked repo's journal records aborted claims (absence-is-the-record survives; the claim journal line is history, not state — maybe the reframe: an aborted claim that was published is just an unclaim, and rollback should SEAL an unclaim rather than reset). Option (c)'s reframe looks strongest by the no-special-case principle but changes rollback from undo to compensate — worth the dialogue.
