## Why

Core already models a ball as a **sequence of incarnations**, not a single
life. Two places say so outright:

- `src/reads/history.rs:1-12` — "A closed/dropped ball deletes its
  `tasks/<id>.md` (§2, no archive dir); **the deletion is not a tombstone but
  older CONTENT**, recoverable most-recent-down from `git log`. […] Taking the
  newest deletion makes a **reused id** unambiguous — **at most one incarnation
  is ever live**, so the most recent dead one is 'the' dead ball."
- `src/id.rs:82` — on `mint`'s `taken` argument: "(`taken` is the **live** id
  set — **a dead incarnation's id is legally reused**, …)"

So `bl show <closed-id>` and `bl list --status closed` already reconstruct dead
balls through `resolve_dead`. Core can **read** the dead set; it just cannot
move one back across the line. That asymmetry is the thing being fixed — this
is the write half of an existing read path, not a new state model.

The "at most one live" invariant needs no enforcement: there is one path,
`tasks/<id>.md`, so a restore cannot violate it by construction.

Balls is unopinionated. Whether reopening a ball is a *good* workflow is the
operator's call, not the tool's. Core's job is to make the transition
expressible and refuse only what is actually ambiguous.

## Scope

`bl reopen <id> [--clean] [-m MSG] [--as ID]` — restore `tasks/<id>.md` from
the newest deletion's parent tree (exactly the content `resolve_dead` already
reconstructs) and commit it to the store branch.

- **Refuse on a live id.** `mint` avoids only the live set, so a dead id can
  legally have been re-minted to an unrelated new ball. Reopening then would
  clobber a stranger. Refuse, naming the collision.
- **Refuse when the id names nothing** — no live file and no deletion in
  history (`resolve_dead` → `None`).
- **Restore verbatim by default.** No implicit stripping: unforced automation
  is unnecessary friction. What was in the frontmatter at close comes back.
- **`--clean`** — restore the ball *fresh*: drop `claimant` (the claim named a
  worktree that close destroyed, so carrying it forward restores a fact that is
  already false). The opt-in is the point — the operator says which they want.

## Not in scope

- Reverting the delivered commit. Close already squashed `work/<id>` to `main`;
  reopening the ball says nothing about that, and conflating them would be the
  tool holding an opinion.
- Plugin mirrors. The github-issues plugin will not reopen the issue, and a
  reclaim mints a second `bl-chore` child. Both are plugin-level.

## Notes for the implementor

- A reclaim of a reopened ball is mechanically ordinary: `materialize` reattaches
  an existing `work/<id>` rather than erroring
  (`src/delivery_repo_acts.rs:29-34`, test
  `materialize_creates_then_is_idempotent_then_reattaches_an_existing_branch`),
  and prime normally pruned that branch anyway, so the reclaim forks fresh from
  `main`. Nothing counts closes per ball.
