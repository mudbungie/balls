`delivery_fold::ensure_no_resurrection` builds its two path sets with git
commands that BOTH do rename detection, but over different diffs — so the
detection can fire on one side and not the other, and the difference is read as
a resurrection:

    let squash   = path_set(diff --name-only <base> <branch>)          // tree-to-tree
    let authored = path_set(log --format= --name-only --cc <branch> ^<base>)  // per-commit

For a rename a->b, `--name-only` prints only the DESTINATION. So if a single
commit's diff pairs a->b (authored = {b}) while the tree-to-tree diff does NOT
pair it (squash = {a, b}), `a` lands in `excess` and the close aborts with
'no-resurrection invariant: ... path(s) never authored on it since its fork'
naming a path the work branch demonstrably authored. The user sees a refusal
they cannot act on.

The asymmetry is reachable because rename detection is not unconditional: it is
bounded by `diff.renameLimit` (and `merge.renameLimit`), and a big tree-to-tree
diff can blow that budget and silently disable pairing while a small single-
commit diff stays under it. Ambient `diff.renames` config differences between
the two invocations do not arise (same repo, same process), so the limit is the
live path. Rare, but it fails CLOSED on a legitimate close, and the operator has
no way to tell it from a real leak.

The fix is the same one flag on both, for the same reason as bl-ae74: the
invariant is about WHICH PATHS A COMMIT TOUCHED, and rename pairing is a
presentation choice that has no business changing that answer. `--no-renames`
on both makes the two sets comparable by construction — every rename reports as
its delete plus its add on both sides, so the subset relation holds whenever the
work branch really did author everything the squash carries.

Needs a test that pins the asymmetry (a fixture with `diff.renameLimit = 1` on
the tree side is the cheap way to force detection off for one of the two reads
without contriving the history).

Found while fixing bl-ae74 (2026-08-07), checking whether any other git read in
the tree shares the swallowed-deletion family. The two `--diff-filter` reads
were the only literal instances; this is the same defect wearing `--name-only`.
