Filed by an agent-fleet coordinator (yog, 2026-07-29) after burning real time on this failure mode four times in one session. This is a **behavioral** complaint, not a bug report: every individual mechanism behaved as documented. The complaint is about what the system tells the operator, and what it does not.

## The failure mode

An agent finishes its work, starts `bl close`, and reports "done". The close is still in the gate. The agent's turn ends. Sometimes the backgrounded close survives its parent and lands; sometimes it dies. Either way the agent has already announced success.

What is left behind when it dies: the ball still `claimed`, the work committed on `work/<id>`, nothing on `main`. That state is **byte-identical** to a healthy close still running its gate. There is no signal that separates them.

Observed four times in one session (agent ids elided): three agents reported completion with no close process alive and the ball still claimed; one agent (bl-df65) I diagnosed as abandoned on exactly the same evidence — stale worktree mtime, branch behind main, zero commits, a claim hours old — and it was alive the whole time and landed cleanly. **Same evidence, opposite truths.** I was right three times and wrong once, and I had no way to know which was which. That is the complaint.

## Why the operator cannot resolve it today

1. **Exit status lies.** A close that delivers, seals, and retires can still exit 1 on `src/mutate_report.rs:73` — panic `"a mutating op always seals a bl-id trailer (§5)"`, observed on yog bl-9130. So the one in-band signal is untrustworthy in the success direction, and the agent that sees it reasonably reports failure. (Separate defect, worth its own ball; noted here because it is why the operator stops trusting `bl` and starts trusting `git log`.)

2. **Verification is entirely out-of-band.** The only reliable check is `git log --oneline` for the commit plus `bl list` for the ball's absence — two commands against two different substrates, neither of which is `bl` telling you what happened. There is no `bl show <id>` field, no verb, nothing that answers "did my close land?"

3. **A claim has an age but no liveness.** `bl list` renders `@worker (5h)`. Age is not progress. Nothing in the store records that a close is in flight, when its gate started, or whether the claimant still exists. `bl prime` reports committed-but-undelivered `work/` branches as crash debris — which is the right instinct, but it fires only at prime time, says "unless an op is running here right now", and puts the judgement back on the operator with no evidence to judge on.

4. **The gate is long enough to guarantee the problem.** ~10 min per attempt, and under concurrent close traffic 3-4 attempts is normal (see bl-9042 — I am adding this session's frequency data to it). A 30-40 minute foreground command is longer than most agent turns want to be, so agents background it, and backgrounding is what detaches the outcome from the reporter.

## What I want, stated as a principle rather than a feature

**A close should be self-reporting, and a claim should carry liveness.** An operator — human or coordinating agent — should be able to ask `bl` alone whether work is progressing, landed, or dead, and get a trustworthy answer without cross-checking git.

Deliberately NOT proposing a mechanism: a heartbeat field, a lease, a `bl status` verb, and a PID stamp are all new state in a store whose whole virtue is that status is derived and never stored, and at least one of them (the lease) is already live tension in bl-9042. Attack the principle first. Possible framings, none endorsed:
- Is "is this claim alive" derivable from what already exists (the work branch's commits vs `main`, the change worktree's presence, the op log tail) rather than stored? If so the fix is a **read**, not a field.
- Is the real defect that `close` is one long opaque call, and the answer is to make its phases legible (folded / gated / delivered / sealed) so an interrupted close reports where it stopped?
- Or is this purely a client-discipline problem — in which case say so in `bl close --skill` in words strong enough that an agent holds the call in the foreground, and the docs become the fix.
