Observed on the lernie store 2026-07-26 during concurrent fleet traffic: an agent's bl close passed the full gate then died at the seal with 'cannot change to .../clones/.../changes/9546e8b...: No such file or directory' — a sibling agent had removed that change worktree mid-op, plausibly by following bl prime's own debris advice ('remove with git worktree remove ...'), which that agent's prime had printed for seven such paths. Damage was one-sided and benign THIS time (code had delivered; the task record went unsealed; a plain retry sealed it, no duplicate commit — the bl-a5f3/bl-8b89 fixes held), but the failure was manufactured by our own advice: prime cannot distinguish crash debris from an op that is merely mid-flight. A change worktree is 'orphaned' only relative to a moment; under fleet concurrency the debris list is a race. Fix directions to weigh: (a) age-gate the advice (only name a change worktree older than some bound — but a bound is a knob); (b) liveness probe (the op's process is gone — but ops are not tracked by pid today, and adding pid state is new mechanism); (c) reframe: the change worktree's OWNING OP is identifiable (its branch/commit carries the op trailer since bl-a5f3 put identity on the wire) — prime could check whether the op's outcome is already sealed in the store and only call it debris when the store shows the op concluded or the worktree's base is stale relative to the store tip. (c) matches the bl-baa0 precedent (closure-aware advice) and adds no state. Related: bl-58b8 (prime deletion-license design) — this finding argues ANY widening of prime's deletion license must come after debris detection is concurrency-safe, and should be weighed in that dialogue.
