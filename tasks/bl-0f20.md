An agent asked to compare balls to beads read the docs (not the code) and concluded balls has no memory story and that closed tasks vanish into git history. Every one of those conclusions is supportable FROM OUR DOCS. Four misses, all docs-only, no code:

1. SKILL.md never mentions recall AT ALL. No --all, no NEEDLE, no -s closed. Its only dead-set line teaches `bl show <id> --json | bl import` — the REOPEN trick — so the agent-facing guide implies closed work is not queryable. Biggest miss: this is the file agents actually read.

2. README:101 is written in the language of loss: "A closed task has no file — absence is the resolution... reconstruct dead tasks from history, walking newest->oldest." "Walking newest->oldest" reads as an implementation confession. Never states the property it BUYS: closed work stays fully queryable at zero context cost, which is exactly why there is nothing to compact.

3. `bl list NEEDLE --all` — full-text over title+body across live AND dead — is never shown anywhere. Both halves sit in the same README table cell; the composition is the actual answer to "can you search closed work." The list --skill examples confirm the gap: every closed-set example is `-s closed --claimant alice`, i.e. ATTRIBUTION ("what did alice deliver"), never RECALL.

4. Self-inflicted: the beads section (README ~300-316) argues only substrate — Dolt vs git, two VCSs, a database binary. It opens "Beads was right about the core insight" and never touches their headline pitch, which is memory, not tracking. An agent reads our own comparison, finds no answer to remember/compaction, and reasonably infers we have none.

SCOPE: SKILL.md gains a recall invariant; README:101 reframed from absence to context economy; `bl list NEEDLE --all` shown in README + `bl list --skill` examples; beads section extended to the memory axis and amended to concede less — balls does what beads does with less overhead, and should say so. The live tree IS the compaction: lossless, zero-token, no summarizer to hallucinate. Their compaction is a lossy cache over a store they chose to keep resident.

Docs only. No interface change (a concurrent ball is speeding up the historic query; that is implementation, and these claims hold regardless).
