## Symptom

On a stock Ubuntu 24.04 LTS box (git 2.43.0), EVERY mutating op
(create/claim/update/close) panics right after sealing:

    thread 'main' panicked at src/mutate_report.rs:73:10:
    a mutating op always seals a bl-id trailer (§5)

The store commit IS written (the op's effect lands), but the post-seal readback
in `sealed_id` finds no `bl-id` trailer and the `.expect()` aborts. So `bl` from
crates.io (0.5.5) is effectively unusable on stock Ubuntu 22.04/24.04 until git
is upgraded.

## Root cause

`message::render` appends trailers with
`git interpret-trailers --if-exists add --trailer …`, feeding the message body
on stdin WITHOUT a trailing newline. `sealed_id` → `message::parse` reads them
back with `git interpret-trailers --parse`.

On git 2.43, `interpret-trailers` does NOT insert the blank-line separator
before the appended trailer block when the input has no trailing newline. The
title and the trailers collapse into a single paragraph, so `--parse` returns
nothing and `bl-id` is absent. git 2.53/2.54 insert the separator regardless,
which is why a dev box on newer git never hits it. Same bl code on both boxes —
`src/message.rs` and `src/mutate_report.rs` are unchanged since the v0.5.5 tag;
the only variable is the git version.

## Minimal repro (no bl needed)

    printf 'gate smoke test' | git interpret-trailers --if-exists add --trailer bl-id=bl-c654

  git 2.43.0 →
      gate smoke test
      bl-id: bl-c654            # merged with the title — NOT a valid trailer block
  git 2.54.0 →
      gate smoke test
                                # blank separator inserted
      bl-id: bl-c654

With a trailing newline (`printf 'gate smoke test\n' | …`) BOTH versions insert
the separator. So the trigger is precisely: newline-less input + old git (2.43
fails, 2.53/2.54 pass; exact boundary version unverified).

Observed store commit on the failing box — the subject swallows the trailers:

    gate smoke test bl-protocol: 1 bl-op: create bl-id: bl-c654 bl-actor: noodlezoo

## Impact

Ubuntu 22.04 (git 2.34) and 24.04 (git 2.43) are the most common server LTSes;
`cargo install balls` then panics on the first mutating op out of the box.
Discovered founding silt's pipeline bl store on noodlezoo (Ubuntu 24.04); worked
around by upgrading git via the git-core PPA (→ 2.54).

## Suggested fix (pick)

1. In `message::render`, ensure the body handed to
   `interpret-trailers --trailer` ends with a newline (append one if absent).
   This makes separator insertion deterministic on every git version — the
   minimal, robust fix. Regression test: a body with no trailing newline
   round-trips render→parse and yields `bl-id`.
2. Defensive twin: in `sealed_id`, if `bl-id` is absent, return an actionable
   `io::Error` (name the git-version pitfall) instead of `.expect()` panicking —
   fail loud and diagnosable, not a raw abort.
3. Optional: document/check a minimum supported git version.
