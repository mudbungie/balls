Design dialogue (living doc: docs/design/ — created on claim). PROBLEM: a dozen agents x a 15-minute close gate = hours of idle serialization; main-merge is the contention point. DIRECTION (converged in dialogue 2026-08-11): an optimistic prefix merge queue — agents never merge each other's code across ownership lines; they speculatively pre-run the gate on QUEUE PREFIXES so every close lands in order as a cache hit. Core reductions: (1) delivery stays per-ball no-ff close, so provenance/log/task-seal are untouched — speculation is pure cache-warming, deletable (severability); (2) queue order is a query over merging-tags (tag-time = position; sealed-while-tagged; any fix requires retag at bottom) — no stored queue; (3) candidates are computed by git merge-tree (no refs, no worktrees — nothing to leak); (4) the builder interface is a verdict record {tree OID, gate fingerprint, verdict, builder} — local or GH Actions both satisfy it, trust reduces to builder identity, close on cache miss just builds locally (offline degrades to stock behavior); (5) scheduling = concurrency cap + nice by queue position; close-time builds preempt speculators; fail-fast staged gate (clippy -> 300-line -> tarpaulin) makes evictions cheap, substituting information for hedging. OPEN: monotone landing rule; conflicted candidates (merge-tree conflict => unbuildable, fold-at-close); hedge policy under free remote capacity; GH wiring (ref TTL, minutes budget). WHY THIS SHAPE: any topology that adds ungated merge nodes adds deferred conflict; with idle agents the objective is latency, not gate-run count — so pre-pay gates, never move delivery off main.
