Observed in yog (`/home/mark/dev/yog`), 2026-07-29, closing ball bl-9130. Cosmetic — filed because it degrades the diagnosability of the close path, not because it loses work.

## What happens

`bl close` removes the `work/<id>` worktree as its final act. An agent that ran the close from **inside** that worktree (the natural place to be — `bl claim` prints that path and all edits happen there) then has a shell whose cwd no longer exists, and git emits:

    fatal: Unable to read current working directory

...around the close's real output. Nothing is lost; the delivery and retire both complete.

## Why it is worth fixing rather than tolerating

It arrives interleaved with the close's genuine diagnostics, at exactly the moment a caller is trying to decide whether the close succeeded. In the run where this was observed, the same output also carried a real panic (bl-dede) and the operator had to sort a `fatal:` that meant nothing from a `panicked at` that meant something. A close's output is the one place noise is expensive: it is what an agent reads to decide whether to retry.

Compounding it: the two other close-path defects filed today (bl-dede, bl-8750) both make callers distrust `bl`'s own reporting. `fatal:` lines that are actually harmless are part of why.

## Shape of the fix

The teardown is correct — the complaint is that it happens without regard for where the caller stands. Options, none endorsed:

- Have `bl close` chdir out of the worktree (to the project root it already knows) before removing it, so no subprocess of the close inherits a deleted cwd.
- Or leave the behavior and **say it**: `bl close --skill` could state that the worktree is removed and that running the close from inside it leaves the caller's shell in a deleted directory, with the one-line fix (`cd` to the project root first). Docs would be an acceptable resolution here given how minor the effect is.

Note the interaction with bl's cwd-keying: the store addressed is keyed on the literal directory you run in, so a caller who has been told to `cd` out needs to land somewhere that still addresses the right store, or use `-C`.

Cross-ref: bl-dede (close exits 1 on success), bl-8750 (close in flight vs abandoned is indistinguishable).
