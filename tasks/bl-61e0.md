A store full of chore-minted children (lernie: five identical 'gate: docs'/'gate: tests' rows) is unreadable flat: the parent relation that disambiguates them is already stored (Task.parent) and already rendered by show's children section, so list is discarding a fact it has.

Design (assessed 2026-07-31, holds):
- Derived, human-render only — same class as claim-age, the fleet label, and the ->bl-xxxx marker. No new stored field, NO new flag: tree becomes the default human render. --json untouched (returns before render; stays the bedrock stored-frontmatter mirror).
- One invariant, no special cases: the tree is a forest over the RENDERED set. After filters+scope produce the rows, a row indents under its parent only if the parent is also in the set; otherwise it is a top-level root. Closed parent, filtered-out parent, foreign parent — all the same path.
- §10 order applies per sibling level instead of globally. Ordering is already declared display-only (never enters ready()), so nothing semantic moves.
- The -> delivery-target marker stays: tree = containment (parent), marker = delivery routing (parent AND close-gate). Distinct facts.
- Dispatch unaffected in practice: under -s ready a claimed parent and its blocked gates are both filtered out, so the ready view stays mostly flat; the tree reshapes the default live view, where the gate noise lives.

Accepted trade, stated plainly: a low-priority parent with high-priority children pulls those children visually below it, weakening the global priority top-to-bottom scan in the default view. Correct anyway — a child is meaningless out of parent context.

Guard against a parent cycle (visited set) rather than trusting the store invariant.
