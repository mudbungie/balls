# Who wrote which comment, computed not stored

`bl comment` (bl-d136) appends to the body. Every append is one commit carrying the author, the timestamp, and the `bl-actor` trailer that `--as` sets. The gap is co-location: reading a body of six comments, you cannot tell whose is whose without `git log -p`.

Close it by DERIVING the byline at render time. Store nothing.

## The mechanism

`git blame` on `tasks/<id>.md` in the store checkout gives per-line commit attribution. Filter to commits whose `bl-op` trailer is `comment`. Each contiguous run of body lines sharing such a commit is exactly one comment.

**The commit boundary IS the comment boundary.** That is the whole trick, and it is why this needs no marker parsing: an append is one commit, so its lines are its lines.

### The `---` rule is still never read

bl-d136 states it and this ball does not weaken it: balls never searches for a rule, counts rules, splits on one, or suppresses one. The renderer inspects NO body byte. It groups lines by blame commit, and emits an ADDED render line at the head of each comment region. Body content passes through unaltered.

## What renders where

- Human `bl show <id>` — each comment region gets a byline: the ISO timestamp and the actor, in the vocabulary the `journal` section already uses (see `src/reads/journal.rs`, which formats `%ct`, `%an`, `bl-op`, `bl-actor` today). Visually subordinate to the text; honor `--plain` (no color, no glyphs).
- Body lines NOT from a `comment` op — the original `create` body, a `--body` rewrite, an `--edit` — get NO byline. They are the living document, not a note.
- `bl show --json` — UNCHANGED. It carries `body` verbatim and no attribution, and it must NOT pay the blame call. Bedrock is the round-trippable mirror of stored state; blame is history, and history cannot survive `show --json | bl import` (import writes new commits under the importer). Same boundary the journal already sits on: derived means human-only.

## Degradation is honest, never an error

Render what blame says. Do not detect, repair, or warn:

- An imported ball collapses onto the import commit — every line attributed to the importer. Correct: that IS who wrote that file.
- A squashed or rewritten tasks branch collapses blame the same way.
- A closed ball still resolves (`bl show` reconstructs from history). Blame it at the revision where the file last existed; `src/reads/journal.rs` already walks live and dead ids alike — mirror its approach rather than inventing one.

An empty body must make no blame call at all.

## Shape

New `src/reads/attribution.rs`, sibling to `journal.rs`, per the decomposition convention. One blame per human show, paid only for a non-empty body — the same cost shape as the journal walk, and bedrock pays neither.

Ask git for structured values rather than hand-parsing: `blame --porcelain` for the line/commit map, and the existing trailer-value technique (`%(trailers:key=bl-op,valueonly=true)`) for the op filter. The §5 no-hand-rolled-parser discipline holds on the read side.

## Coverage

100%, and the degradation paths are the work: a comment region annotated; a `create` body left bare; a `--body` rewrite left bare; an imported ball (all one commit); a closed ball; an empty body (no blame call).

## Docs

`skill/comment.md` and `skill/show.md` both need the byline described, including plainly that it is derived and therefore human-only — `--json` will never carry it. Amend `docs/architecture.md` §9 (show render) and add the decision record.

---

IMPLEMENTED, with one recorded deviation: the byline hangs at the TAIL of each comment region, not the head.

Verified against real blame: `appended_body` writes `{existing}\n\n---\n\n{text}\n`, so a comment commit's lines are always [blank, ---, blank, text...]. The HEAD of every region is therefore decoration — a byline there lands directly under the PREVIOUS comment's last line of text and ABOVE its own rule, so it reads as the previous comment's. Adding a blank line above it only leaves it floating between two comments, still above its own rule. The TAIL is always the comment's own last line of text, so a byline there is adjacent to exactly what it attributes and never touches the rule.

Not a taste call about headers-vs-signatures: head placement is wrong output given where the decoration sits, and the constraint that balls never reads the rule is exactly what forbids skipping past it. Everything else in this ball is implemented as specified — reasoning at full length in docs/design/bl-236c-comment-attribution.md.
