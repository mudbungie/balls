Observed 2026-08-03 in yog under ~6 concurrent agents (ball bl-3c28, agent search-wright).

A `bl close` run passed its gate and DELIVERED the code to main, then its final task-file seal lost a race to a concurrent `bl`, reporting: "the store moved under this op — nothing was written". Net state: the delivery commit is on main, but `bl list` still shows the ball CLAIMED and the worktree still up. A bare re-run of `bl close` sealed it cleanly (exit 0) without re-delivering, so the recovery path works — but only if the operator knows to try it.

Why it matters: the two halves of close (deliver, seal) are not atomic with respect to a concurrent store write. The intermediate state reads exactly like 'the close failed, my work did not land' — which is the opposite of the truth, and invites an agent to redo delivered work or an operator to unclaim a ball whose code is already on main. Three agents in the same session separately mistook a stalled/failed close for undelivered work.

`bl close --skill` documents the CAS on the delivery ref ('the loser aborts loudly (nothing overwritten) — just re-run bl close'), but that text is about the delivery ref move; it does not describe this case, where delivery SUCCEEDED and the store seal lost.

Wanted, in preference order:
1. Make the seal retry on a moved store, so close is atomic from the caller's view.
2. Failing that, make the failure message say what actually happened — that the code delivered and only the seal is outstanding, and that a bare re-run finishes it — so the state is not mistaken for a failed delivery.

Verify against the current balls tree before ruling; this body is an observation from the consumer side, not a diagnosis of the store code.
