Observed 2026-09-18: five agents closing in parallel. Since bl-a1a4, close REFUSES when the target (main) moved and is not merged into work/<id> — the agent must `git merge main` in its worktree, re-run the gate (~2 min tarpaulin, unless the verdict cache hits), and retry. Every landing moves main, so N concurrent closes cost O(N^2) gate runs in the worst case: bl-6a84 lost the race four times (to bl-e8ed, bl-1643, bl-816b, bl-3b82) before landing on the fifth attempt; bl-3b82 lost twice. Nothing broke — the refusal is correct (close validates, you reconcile) — but the throughput cost is real, and the speculative merge queue (bl-24e7) only helps when a speculator pre-builds the exact folded tree.

A second writer to main compounds it: GitHub merges release-plz PRs onto origin/main, so local main and origin/main diverge and bl-pushmain's close.post push is rejected non-ff (2026-09-25, hand-merged).

The user wants this handled correctly and will drive the design personally — do not implement from this body. Open questions: should the queue own ordering (one writer, closes enqueue)? Should a clean fold of unrelated files be re-gated at all, or can a verdict be composed from (base verdict, disjoint diff)? How does the one-writer model admit GitHub's release merges? Design deliverable is a doc under docs/design/, per the repo's design practice.
