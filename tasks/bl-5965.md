From CONVERGED docs/design/bl-0161-cross-repo-work.md (Q2 + labels, ratified 2026-07-04). Today bl list in repo A shows repo B's balls as ready while claim refuses them — list computes a different predicate than claim enforces. Maintainer's model, confirmed verbatim: 'there is an implicit --repo=this-one (or whatever the syntax is) when issuing that command? which is overridable, of course, and the --everywhere (or whatever interface) flag is really just omitting the filter?'

DELIVERABLES. (1) list's default set becomes the claim-admitted set — ONE shared predicate with the guard (built on bl-ac6f's root-SET read): balls whose root matches this checkout's root set, plus rootless balls; a rootless checkout (non-git dir) admits everything, so single-store usage is byte-identical to today. (2) --everywhere omits the scope predicate; composes with -s/--tag/needle unchanged (--everywhere -s ready = fleet dispatch query). show stays global (naming an id is the explicit signal). (3) Foreign rows under --everywhere render a label: match the ball's root against each enrolled checkout's computed root (this box's XDG clone entries) and render that checkout's directory basename; short hash for repos this box never primed. RENDER-TIME ONLY — maintainer verbatim: 'pure render-time sugar. Doesn't appear in --json, just something that shows nicely when someone is looking at the task.'

BOUNDARIES. --json byte-identical (bedrock = stored frontmatter, root_commit already rides it). Root read is lazy — a catalog with zero rooted balls never shells git (task-only stores stay walk-free); once per invocation, never per ball; do NOT cache the root anywhere durable (drifts at exactly the history-rewrite moment it matters). No --repo=X selector (nothing to name; cd is the signal). The owner-authored hash→label config legend is NOT built — documented last resort only if basename derivation hurts in practice.
