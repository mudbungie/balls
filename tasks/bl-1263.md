Foundation of the speculative merge queue (design: docs/design/bl-24e7-speculative-merge-queue.md). The record {tree_oid, gate_fingerprint, verdict, builder} IS the builder interface — everything else (speculators, GH Actions, scheduling) is a policy that reads or writes it. Work: (1) record format + store — decide the home here (open Q3 of the design: center store travels with the fleet vs local XDG matching trust=builder-identity; attack both, pick one); (2) gate_fingerprint = hash of toolchain + gate config so a clippy bump silently invalidates stale verdicts; (3) the consumer: the pre-commit gate consults the store by folded-tree OID and exits clean on hit — if this lands entirely in the hook/close.pre chain, the core is untouched and severability is total (delete the store, stock behavior returns via cache miss). WHY: the gate verdict is a pure function of the tree; content-addressing makes 'stated build matches the merge' inherent rather than checked, and reduces all trust to builder identity.
