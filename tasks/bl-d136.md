# `bl comment <id> "TEXT"`

Sugar over `bl update`, nothing more: read the stored body, append TEXT, run the normal update seal. It exists because "comment" is the word people reach for — making them discover `-m` on `update` under a heading called "Body vs journal" is why notes never landed (bl-0c50).

## Why the body and not the journal

The journal (`-m`, store-branch git history) is DERIVED, so bedrock `--json` cannot carry it: `bl show` and `bl show --json` disagree about what the ball says. The body is STORED state — `--json` carries `body` (the record went total for import round-trip, architecture ~L2748) and the human render prints it.

Appending to the body is the one place a note lands in both views with no new mechanism. That is the entire justification for this verb; if it did not render in both, it would not be worth building.

## No stamp, no attribution, no marker

The append is the literal text, separated from the existing body by a blank line. Nothing else. The commit records who and when — putting a stamp in the body would be a second copy of a fact git already owns authoritatively, and a copy that can drift (hand-edited through `--edit`, re-imported through `bl import`).

Consequences, all intended:

- The body stays OPAQUE markdown. balls parses none of it, so `--edit` cannot corrupt a structure and `--body` still overwrites wholesale — a comment IS body, and rewriting the body means rewriting it. No section boundary, no marker to find.
- Rendering is free in both views. There is nothing to build for it.
- Two concurrent comments conflict textually like any two writes to one file; the existing seal/CAS handles it exactly as it handles any concurrent body write. No new path.

## Surface

    bl comment <id> "TEXT" [--as ID]

No `-m`: echoing the text into the commit note would store one fact twice. The commit subject derives from the op, and the diff already shows the text.

No stdin flag — `bl comment bl-1a2b "$(cat notes.md)"` already works.

Empty or whitespace-only TEXT is REFUSED: a no-op append would seal nothing, which is the bl-cf93 silent-note-loss failure in a new costume.

## Wiring

`Verb::Comment`, `OpClass::Mutating`. `Verb::ALL` feeds the parser, `bl help`, and the hook keys, so `comment.pre`/`comment.post` come free. Because `Verb` IS a blocker edge's `on` type, `--needs X:comment` becomes expressible — harmless, and it needs no special-casing.
