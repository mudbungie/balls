`Project::contained(branch, X)` (src/delivery_standing.rs:84) is one shared
predicate — "is a content-merge of `branch` into `X` a no-op?" — read by two
callers that pass DIFFERENT `X`:

- `standing()` (delivery_standing.rs:51) passes the `[bl-id]`-tagged **delivery
  commit** found since the fork (`delivered_since_fork`).
- prune's closed-ball debris arm (delivery_prune.rs:128) passes the
  **integration tip** (`main`).

Both are deliberate and documented — `contained`'s own docstring says the prune
"asks the same question of the integration TIP, where containment means the
branch is safe to delete even though no `[bl-id]` delivery ever tagged it", and
delivery_prune.rs:111 justifies the tip as the way to see content that landed
inside ANOTHER ball's squash. So this is not sloppiness; it is two answers to
two genuinely different questions ("did MY delivery carry this?" vs "would
deleting this lose anything?").

WHAT IS WRONG IS THE MISMATCH ITSELF, and §11 nested delivery is what turned it
from a defensible split into a hole: a ball whose parent close-gates it delivers
into `work/<parent>`, NOT into integration. Neither caller knows that. Both
hardcode the integration branch as the reference at exactly the point where the
delivery TARGET became per-ball.

Observed, and it is the COMMON case here, not an edge: bl-chore mints an
"Update the docs" child for every claimed ball in this repo, and every one of
those is a nested delivery. So `bl prime` — the thing the skill guide tells an
operator to run when things are weird — routinely prints

    work/bl-3f97 ... its content is NOT contained in main — read it with
    git diff main...work/bl-3f97, then discard with git branch -D work/bl-3f97

for a chore child whose content is sitting safely on `work/bl-0c50`, its actual
delivery target. The operator is sent to read and adjudicate a 33-line diff
about work that was never stranded. The false-alarm direction is confirmed too:
prime said the same of `work/bl-f389` while its content is on `main` verbatim
(its parent bl-dede had landed) — a nested child's branch also carries its
PARENT's then-unlanded work, so containment-vs-main is answering about the wrong
content set in both directions.

DIRECTION IS DELIBERATELY UNDECIDED — file the mismatch, converge the fix by
dialogue. Both readings are live:

- Target-relative: the reference should be the ball's §11 delivery target,
  falling back to integration for a parentless ball. Makes both callers ask one
  question against one per-ball reference. Cost below.
- Integration-tip-is-right-for-prune: prune's question is only "is deletion
  safe," and deleting a nested child's branch IS safe whenever the parent's ref
  holds the content — so the tip may be the correct conservative reference and
  the real defect is only the VOICE (it reports a diff to read instead of naming
  the target the content is on).

The constraint that makes it non-trivial, and the reason not to pick blind: the
prune arm fires precisely when the ball is CLOSED (no task file — absence is the
record, delivery_prune.rs:101), so `parent` and the close-gate that together
constitute the §11 nesting declaration are GONE from the live store. The target
is recoverable only by the `show`-style history walk. Whether the debris report
should pay a history walk per branch, or whether the answer is a cheaper voice
change, is the design question.

Not urgent: nothing is lost today, prune only REPORTS ("Prunes neither arm —
reporting is the whole contract"). The cost is operator attention and a standing
invitation to `git branch -D` after misreading a diff.
